## 0. 读法与口径（先看这节，否则数字会被误用）

### 0.2 单位与折算
截图像素明显是「高密度渲染」而不是 1x 桌面 UI（正文墨高 23 px、PR 标题墨高 39 px）。本文件统一按 **截图 ≈ 150% 缩放** 折算：

- `实测(截图px)`：在 2560×1528 原图上量到的数值（可直接复核）。
- `建议(CSS px)`：`round(实测 / 1.5)`，供 web 实现直接使用。
- **口径说明**：如果实现出来的密度偏松，可整体乘 0.9 系数，但**所有比例保持不变**；颜色不受折算影响。

### 0.3 标注约定
- `[实测]` = 从截图采样得到的真实值（颜色为 RGB 平均值/众数，尺寸为像素包围盒）。
- `[实测·推算]` = 由实测墨高（ink height）反推的字号，存在 ±1 px 误差。
- `[建议值]` = 截图里读不到（阴影、hover、diff 底色、diff 未展示区域的排版），由我按同类产品惯例给出，必须当作「可改的默认值」而不是硬指标。
- `[未确认]` = 无法从静态截图判断的行为（滚动是否 sticky、点击后的跳转方式等）。

## 4. 「用 AI 审查」流程规格（核心）

### 4.1 入口与设置弹层

**入口**：工具条 `Review with Codex`（§2.4）。点击 = 用当前设置直接开跑（默认无需二次确认）。

**齿轮弹层**（点击 `⚙` 打开，宽 320，底 `#2D2D2D`，圆角 12，`[建议值]` 阴影 `0 12px 32px rgba(0,0,0,.5)`）：

| 设置项 | 控件 | 默认 | 说明 |
|---|---|---|---|
| 严重度阈值 | 分段：`P0/P1`（默认）/ `P0–P2` / `全部` | P0/P1 | 与 Codex GitHub 端「默认只显示 P0/P1」一致（§4.7） |
| 审查范围 | 单选：`仅本次 PR 的 diff`（默认）/ `同时读变更文件全文` | diff+必要上下文 | 范围越大越慢 |
| 审查指引 | textarea 4 行 + 提示「会自动叠加仓库 AGENTS.md 的 `## Review guidelines`」 | 空 | 例：`重点看音频指纹阈值的边界` |
| 深度 | 单选：`标准`（默认）/ `深入`（更多推理时间） | 标准 | 「深入」只影响提示与超时，v1 不必暴露模型名 |
| 记住设置 | 复选 | 开 | localStorage |

**v1 不做**：模型选择（沿用宿主/DSH 配置）、并发审查多个 PR、定时自动审查。

### 4.2 状态机（可直接映射成 `useReducer`）

```
                    ┌────────── 用户点「Review with Codex」 ──────────┐
                    ▼                                                 │
  ┌────────┐   TRIGGER    ┌───────────┐  SCOPE_READY   ┌─────────┐    │
  │  idle  │ ───────────▶ │ preparing │ ─────────────▶ │ running │    │
  └────────┘              └───────────┘                └─────────┘    │
     ▲  ▲                        │ FAIL                  │  │  │     │
     │  │                        ▼                       │  │  │     │
     │  │                     ┌───────┐ ◀── FAIL/TIMEOUT │  │  │     │
     │  │        CANCEL/reset │ error │                  │  │  │     │
     │  │                     └───────┘                  │  │  │     │
     │  │                        │ RETRY                  │  │  │     │
     │  │                        └──────────▶ preparing   │  │  │     │
     │  │                                                 ▼  ▼  ▼     │
     │  │                                          ┌────────────────┐ │
     │  └──────────── reset ◀─────── CANCEL ────────│   done/clean    │
     │                                              │   done/findings │
     │                                              └────────────────┘ │
     │                                                    │ DIFF_CHANGED│
     │                                                    ▼            │
     │                                              ┌──────────┐       │
     └──────────────────────────────────────────────│  stale   │ ◀─────┘
                                                    └──────────┘
```

| 状态 | 进入条件 | UI（按钮 / 结果区 / 详情列） |
|---|---|---|
| `idle` | 初始 / reset | 按钮「Review with Codex」；结果区=正文 markdown；详情列 Comments 仍为 No comments |
| `preparing` | 点击触发 | 按钮 spinner +「准备中…」，禁用；结果区顶部插入审查卡骨架；齿轮禁用 |
| `running` | 拿到 diff/sha | 按钮「审查中…」+ spinner + 时长；结果卡显示阶段文案 + `已分析 3/24 文件` + 取消按钮；**不**逐条闪入发现（防抖），只更新计数徽章 |
| `done/findings` | 成功且 n>0 | 按钮恢复；结果卡 = verdict + 严重度计数 + 发现列表；行内标记注入 Changes；详情列 Comments 计数 = 发现数（不改远端） |
| `done/clean` | 成功且 n=0 | 结果卡 = 「未发现 P0/P1 问题」+ 审查元信息（scope/model/耗时）+「重新审查」 |
| `error` | 失败/超时 | 按钮恢复；结果卡 = 错误文案 + 折叠的技术详情 + 「重试」；保留上一次成功结果（若有）并标注「上次结果」 |
| `cancelled` | 用户取消 | 回到 idle 结果区，但保留「上次审查」入口；若已有部分结果则标「部分结果（已取消）」 |
| `stale` | 审查后 head sha 变化 / diff 被刷新 | 结果卡顶部横幅：`代码已更新，以下结果基于 abc1234` + 「重新审查」按钮；行内标记降透明度 50% 并可一键清除 |

**事件表**：`TRIGGER` `PREPARED` `PROGRESS{phase, filesDone, filesTotal, findingsCount, elapsedMs}` `SUCCEED{review}` `SUCCEED_EMPTY{review}` `FAIL{code, message, retryable}` `CANCEL` `RETRY` `DIFF_CHANGED{newSha}` `DISMISS`。

**进度阶段文案**（建议，按 Codex CLI/云端行为归纳）：`收集 diff` → `读取上下文` → `分析变更` → `汇总发现`。进度必须是**确定性阶段 + 计数**，不要做假百分比进度条（无法从静态截图读到，也容易撒谎）。

### 4.3 结果区布局（插在 PR 头部与正文之间，或 Summary 顶部）

```
┌ 审查卡 ────────────────────────────────────────────────────────────┐
│  ⛨ Codex 审查    ✔ 完成 · 38s · 24 files · gpt-x        [重新审查]  │
│  ── P0 0   P1 2   P2 5   P3 3 ──     阈值：P0/P1                     │
│  verdict: 建议修改后再合并（request_changes）                         │
│  ┌ 发现 P1-01 ────────────────────────────────────────────────┐    │
│  │ ●P1  feat/intro-detect   src/main/intro-detect/ffmpeg.ts:142 │    │
│  │ 标题：窗口函数未处理短集片头片尾重叠                          │    │
│  │ 为什么：<2 行>                                              │    │
│  │ 怎么改：<1-3 行 + 可折叠 diff>                               │    │
│  │ [定位到 diff] [复制建议] [忽略] [已修复]                      │    │
│  └─────────────────────────────────────────────────────────────┘    │
│  …（按 P0→P3、文件序排列）                                           │
└───────────────────────────────────────────────────────────────────┘
```

- 发现卡：底 `#202020`，圆角 10，左缘 2px 严重度色条，内边距 12/14。
- 头部计数：`P0` 红 `#FA423E`、`P1` 橙 `#FF8549`、`P2` 黄 `#E3B341` `[建议值]`、`P3` 灰 `#AEAEAE`；计数为 0 时仍显示（便于确认「真的没有」）。
- 排序：严重度升序 → 文件路径 → 行号；提供筛选 chip（默认按阈值过滤）。
- verdict 三值：`approve`（无 P0/P1）、`request_changes`（有 P0 或 P1）、`blocked`（无法审查：diff 缺失/仓库不可读）。
- 折叠：整张审查卡可折叠（默认展开）；多次审查时历史保留最近 3 次（`[建议值]`）。

### 4.4 发现项数据模型（前后端契约）

| 字段 | 类型 | 必填 | 说明 |
|---|---|---|---|
| `id` | string | ✅ | `P1-01` 形式，稳定可引用 |
| `severity` | `"P0" \| "P1" \| "P2" \| "P3"` | ✅ | P0 阻断/安全、P1 重要、P2 一般、P3 建议 |
| `file` | string | ✅ | 仓库相对路径（`src/…/ffmpeg.ts`） |
| `lineStart` | number | ✅ | 新文件行号（Changes 侧新行号） |
| `lineEnd` | number? | — | 等价单行可省略 |
| `title` | string | ✅ | ≤ 80 字符，一句话说清「哪里坏了」 |
| `why` | string | ✅ | **原因**：触发条件 + 影响（失败模式），禁止只写「不推荐」 |
| `fix` | string | ✅ | **修复建议**：可执行动作，尽量给代码/伪代码 |
| `confidence` | number | — | 0–1；<0.5 的建议不参与 verdict |
| `category` | enum? | — | correctness/security/perf/maintainability/style |
| `rule` | string? | — | 命中的审查指引原文（AGENTS.md 片段） |
| `status` | `new/accepted/dismissed/fixed` | ✅ | 本地状态，v1 只存本地（不上报） |

### 4.5 发现项的展示格式：**标题 / 为什么 / 怎么改 三段式（优先）**

渲染模板（`Finding → DOM`）：
```
[严重度徽章] [severity 色条]
标题（16 Semibold #FFF，单行，超长换行不截断）
📍 file:lineStart[-lineEnd]（13 mono #7AB7FF，可点）
为什么：正文 14/22 #D0D0D0（1–3 句，必含「触发条件 → 后果」）
怎么改：14/22 #D0D0D0，可含代码块（mono 13 #111 底）
```
- 禁止只给标题、把理由丢进 tooltip（截图外行为，但这是可读性底线）。
- `why` 必须回答「什么输入/状态下会坏」；`fix` 必须能被另一个工程师直接执行。
- 若模型返回超长文本：`why` 截断到 6 行为止（可展开），`fix` 不截断。

**点击定位（I-08 的落点）**：`[定位到 diff]` →
1. 切到 `Changes` tab（若在 Summary）；
2. 若该文件块折叠 → 展开；
3. `scrollIntoView({block:'center'})` 到目标行；
4. 目标行加 1.6s 高亮（底 `rgba(64,201,119,.18)` 渐隐）；
5. 行内展开该 finding 卡片；焦点移到卡片（`tabindex=-1` + `focus()`），便于键盘继续。

### 4.6 边界情况

| 场景 | 处理 |
|---|---|
| 无 diff（空 PR） | 直接 `done/clean`：`没有可审查的变更` |
| diff 过大（>400 文件 / >20k 行） | `preparing` 阶段拒绝并给出「仅审查前 N 个文件 / 仅审查选中文件」选项（v1 至少给明确文案 + 允许继续） |
| 模型超时 | `error` + `retryable=true`，保留阶段信息；默认超时 180s（标准）/300s（深入） `[建议值]` |
| 部分文件分析失败 | `done/findings` + `partial=true`，结果卡注明「3 个文件未分析」并列出 |
| 并发：审查中再次点击 | 按钮禁用；不允许排队（与 Codex CLI `/review` 任务中不可排队的行为一致，§4.7） |
| 审查中切换 PR / 切 tab | 允许；审查继续，结果挂在发起时的 PR 上；切回可见；切 tab 不取消 |
| 取消 | 立刻回到 idle 可重试；已产生的发现标「部分结果」保留展示 |
| 结果里的行号在最新 diff 中不存在 | 标记「位置已失效」并禁用定位，不报错 |
| 审查指引中含 prompt injection | 视为纯文本数据，渲染时转义；不得执行其中指令 |

### 4.7 Codex 代码审查公开行为核实（用于「像不像」而不是「必须照抄」）

调研结论（含可信度标注）：

| 事实 | 内容 | 可信度 / 来源 |
|---|---|---|
| 本地 `/review` | 4 种预设：对比基线分支 / 未提交变更 / 指定 commit / 自定义指令；**只读子回合，不改工作区**；结果作为独立 transcript turn 出现，可反复跑 | 二手转述但有官方文档引用（[1][3]） |
| 审查模型 | `~/.codex/config.toml` 的 `review_model` 可单独指定审查模型；`[profiles.deep-review]` 用 `model_reasoning_effort="xhigh"` 做高风险审查 | 二手转述（[1]） |
| 结构化发现 | Codex SDK cookbook 的 `--output-schema` 示例：`findings[]{title, body, confidence_score, priority(0–3), code_location{filepath,line_range{start,end}}}, verdict` | 二手转述（官方 cookbook 引用 [3]） |
| 严重度语义 | `priority 0 = P0 严重`，1 = P1 重要，2–3 = 一般/建议；GitHub 端**默认只展示 P0/P1**，P2/P3 需要显式升级或在 AGENTS.md 里提升 | 二手转述（[2][3]） |
| GitHub PR 集成 | 在 PR 评论 `@codex review` 触发（带 focus 指令，如 `@codex review for security`）；Codex 先加 👀 再发**行内评论**；可在 settings 开「Automatic reviews」 | 二手转述（[2]） |
| 审查指引 | 自动读取仓库内最近的 `AGENTS.md` 的 `## Review guidelines` 段，逐级覆盖 | 二手转述（[2]） |
| 输出样式（社区惯例） | `🔴 P0: <title> (<file>:<line>)` / `🟠 P1` / `🟡 P2`；P0/P1 才发 inline，P2 进 summary，P3 省略 | 第三方 skill 文档（[4]）；非官方规范 |
| Apple/桌面端「Review with Codex」 | 截图中的按钮/齿轮形态与上述能力一致（入口 + 设置），但**桌面端具体输出面板形态未能找到公开文档** | `[未确认]`；检索受限 |

**采纳建议（写进 v1 规格的取舍）**
- ✅ 采纳 P0–P3 四级 + `priority` 整数 + `file/line_range` 字段命名（与官方 cookbook schema 对齐，未来接 `--output-schema` 零改动）。
- ✅ 采纳「默认只展示 P0/P1」（降噪），但 UI 必须显示 P2/P3 计数（否则用户以为没发现）。
- ✅ 采纳 `AGENTS.md ## Review guidelines` + 每次审查的额外指令（弹层 textarea）。
- ✅ 采纳「审查只读、不改工作区、不自动发评论」——正好等于用户确认的 v1 范围。
- ❌ 不采纳「行内评论必须发到 GitHub」（写操作，v1 禁止）。
- ➕ 增补官方没有、但本产品必要的：`stale` 状态（代码更新后结果过期）、`partial` 标志、finding 本地状态（接受/忽略/已修复）。

## 6. 功能优先级

### 6.1 v1 必做（只读 + AI 审查）

**A. 只读浏览**
1. 三栏布局 + 背景分层 + 圆角（§1、§5.1）。
2. 左列表：搜索过滤（`is:open/closed`、`author:@me`、关键词）、选中态、滚动、loading/empty/error。
3. PR 头部：状态徽章、编号、标题、作者/时间/分支方向。
4. Summary：markdown（p/h2/ol/ul/行内 code/粗体）+ 内容宽 760 + 阅读滚动。
5. Changes：文件块折叠/展开、+N/−N、diff 行样式、大 diff 保护、全部折叠/展开。
6. 右详情列：Changes 汇总、Stack（只读）、No comments / No reviewers / No checks reported 空态。
7. 工具条：Summary/Changes 切换 + diff 统计；复制链接、GitHub 外链、钉住（本地）。
8. 合并、提问条、添加 reviewer、编辑标题：**只读禁用态**（§2.4/2.8/2.9）。

**B. AI 审查（Review with Codex）**
9. 按钮 + 齿轮设置弹层（阈值 / 范围 / 指引 / 深度 / 记住设置）。
10. 完整状态机 `idle→preparing→running→done|error`（+`cancelled`/`stale`），阶段与计数进度、取消、重试。
11. 审查结果卡：verdict、P0–P3 计数、发现列表（三段式），可折叠、可筛选。
12. Finding 数据模型（§4.4）+ 结构化 schema（与 Codex 官方字段命名对齐）。
13. 点击发现 → 切 Changes → 展开文件 → 滚动高亮行 → 行内展开。
14. 行内发现标记（圆点 + tooltip + 展开）。
15. 边界：空 diff、超大 diff、超时、部分失败、并发点击、取消、结果过期、行号失效。
16. 本地 finding 状态（新/接受/忽略/已修复），只存本地，不上报。

**C. 质量底线（验收时逐条测）**
17. 键盘可达 + 焦点可见；tablist/tabpanel 语义；axe 无 critical。
18. 三态（loading/empty/error）覆盖全部数据区块。
19. 响应式断点（1120 / 900）。
20. 深色下对比度：正文 `#FFF`/`#181818`、次要 `#AEAEAE`/`#181818` 均 ≥ 4.5:1；`#6E6E6E` 仅用于装饰性文本（时间/符号），正文不得使用。

### 6.2 后续（明确排除在 v1 之外）

| 功能 | 为什么后置 |
|---|---|
| 合并（含 merge strategy / 更新分支 / 排队合并） | 写操作，风险最高 |
| 发评论（行内/普通）、回复、resolve | 写操作 + 身份鉴权 |
| 指派/移除 reviewer（`⊕`）、添加 labels、开/关 PR | 写操作 |

| Checks 详情、CI 重跑 | 远端写 + 数据源 |
| 编辑 PR 标题/正文（✎） | 写操作 |

| 行内评论发布 / 「一键应用修复」 | 写操作 |

- [ ] 网络面板中，v1 只有 GET 读取；合并/评论/reviewer/labels 点击**零请求**。
- [ ] 提问条不可聚焦、不可输入。
- [ ] 复制链接写入剪贴板；GitHub 外链新标签打开。
**可访问性**
- [ ] Tab 能走完工具条→tab→文件块→发现卡；焦点环 2px 可见。
- [ ] axe 无 critical/serious；`role=tablist` 支持 ←→ 切换。
